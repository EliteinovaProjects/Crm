# Deploying the CRM (Frontend + Backend + Neon Database)

This guide walks through deploying:

| Part | Technology | Platform |
|------|------------|----------|
| `backend/` | FastAPI + SQLAlchemy + Alembic | Vercel (Python Serverless) |
| `frontend/` | Vite + React (SPA) | Vercel (Static) |
| Database | PostgreSQL | Neon |

There are **two ways** to deploy on Vercel:

1. **One Vercel project with Services** (monorepo) — matches the "New Project →
   Services" screen you are on. `frontend` and `backend` live in a single
   project and are routed by path (`/` and `/api`). See
   [Option A](#option-a--single-vercel-project-with-services).
2. **Two separate Vercel projects** — the most predictable setup. The backend
   gets its own URL and the frontend points at it with `VITE_API_URL`. See
   [Option B](#option-b--two-separate-vercel-projects).

Both use the same code; the only difference is configuration.

## Quick start — do these steps in order

> Follow these literally, top to bottom. Commands are for **Windows PowerShell**
> unless noted. Replace the `********` placeholders with your real values.

### PART 1 — Create the Neon database (browser)

1. Open <https://console.neon.tech> and sign in (GitHub login is fine).
2. Click **New Project**. **Project name:** `crm`. **Region:** pick the one closest
   to your users (e.g. `AWS US East 2`). Click **Create project**.
3. Wait for the project to finish provisioning, then open the
   **Connect to your branch** dialog (Dashboard → **Connect**).
4. In that dialog set:
   - **Branch:** `production` (Default)
   - **Compute:** `Primary` (Active)
   - **Database:** `neondb`
   - **Role:** `neondb_owner`
   - **Connection pooling:** **ON** (toggle green) ← required for Vercel
5. Click **Copy snippet**. You now have the **pooled** URL. It looks like:
   ```
   postgresql://neondb_owner:********@ep-nameless-bird-aoxabp16-pooler.c-4.us-east-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require
   ```
   Paste it somewhere safe. Call this **[POOLED URL]**.
6. Now turn **Connection pooling OFF** and click **Copy snippet** again. This URL
   has **no** `-pooler` in the host. Call this **[DIRECT URL]**.
7. Turn **Connection pooling back ON**.

### PART 2 — Create the tables in Neon (run migrations from your PC)

> ⚠️ **Important:** the original baseline migration was empty (it only had
> `pass`), so `alembic upgrade head` created *only* the `alembic_version` table.
> It has been replaced with a real autogenerated **initial migration**
> (`alembic/versions/7cdabde502d3_initial_migration.py`) that creates all 31
> application tables. If you already ran the old one, see **PART 2b** below.

8. Open a terminal and go to the backend:
   ```
   cd c:\arjun\Crm\backend
   ```
9. Point Alembic at the **DIRECT** Neon URL and run the migrations (using the
   bundled virtualenv so the dependencies are available):
   ```
   $env:DATABASE_URL="PASTE_[DIRECT_URL]_HERE"
   .\venv\Scripts\python.exe -m alembic upgrade head
   ```
   (macOS/Linux: `export DATABASE_URL="..."` then `./venv/bin/alembic upgrade head`.)
10. You should see `Running upgrade  -> 7cdabde502d3, initial migration` and all
    tables will be created in Neon (users, leads, etc.).

> **How the migration was (re)generated** — the standard Alembic workflow:
> ```
> cd backend
> alembic init alembic                                # already done in this repo
> alembic revision --autogenerate -m "initial migration"
> alembic upgrade head
> ```
> `alembic revision --autogenerate` compares your models (`app/models`) against
> the database and writes the `CREATE TABLE` statements into a new file under
> `alembic/versions/`. When you change a model later, repeat those two commands
> (`revision --autogenerate` then `upgrade head`) against Neon using the
> **direct** URL.

### PART 2b — If you already ran it and only see `alembic_version`

The old (empty) baseline was already stamped in your Neon database, so
re-running `alembic upgrade head` will say "already up to date" and do nothing.
Pick **one** of these to fix it:

**Option 1 — reset the stamp and re-run (recommended):**

```
# In the Neon SQL Editor, run:
DROP TABLE IF EXISTS alembic_version;
```
```
# Then back in your terminal:
$env:DATABASE_URL="PASTE_[DIRECT_URL]_HERE"
.\venv\Scripts\python.exe -m alembic upgrade head
```

**Option 2 — run the ready-made SQL script instead (no Python needed):**

`backend/seed_live.sql` contains the full schema **and** the two seed users.
Open it, copy everything, paste into the Neon **SQL Editor**, and Run. It is
idempotent (`CREATE TABLE IF NOT EXISTS` / `ON CONFLICT DO NOTHING`).

After either option, verify in the Neon SQL Editor:
```sql
SELECT count(*) FROM information_schema.tables WHERE table_schema = 'public';
-- expect 32 (31 app tables + alembic_version)
SELECT username, role, is_active FROM users ORDER BY username;
```

### PART 3 — Make your local `.env` point at Neon (optional)

11. Open `backend/.env` and set the pooled URL (so local runs use Neon too):
    ```
    DATABASE_URL=PASTE_[POOLED_URL]_HERE
    SECRET_KEY=PASTE_A_LONG_RANDOM_STRING_HERE
    ALGORITHM=HS256
    ACCESS_TOKEN_EXPIRE_MINUTES=30
    REDIS_URL=redis://localhost:6379/0
    CORS_ORIGINS_RAW=http://localhost:5173,http://localhost:3000
    ```
12. Generate a secret key with:
    ```
    python -c "import secrets;print(secrets.token_hex(32))"
    ```
    Copy the output into `SECRET_KEY`.

### PART 4 — Deploy the BACKEND on Vercel (browser)

13. Open <https://vercel.com/new> and import the GitHub repo
    `eliteinovapythonbackend21-cyber/Crm`.
14. **Project Name:** `crm-backend`.
15. Click **Edit** next to **Root Directory** and select the **`backend`** folder.
16. **Framework Preset:** leave what Vercel auto-detects (**FastAPI**). Do not change it.
17. Expand **Environment Variables** and add each row (Name → Value), one at a time:
    1. `DATABASE_URL` → **[POOLED URL]**
    2. `SECRET_KEY` → the random string from step 12
    3. `ALGORITHM` → `HS256`
    4. `ACCESS_TOKEN_EXPIRE_MINUTES` → `30`
    5. `REDIS_URL` → `redis://localhost:6379/0`
    6. `CORS_ORIGINS_RAW` → `http://localhost:5173` (we add the real frontend URL in step 27)
18. Click **Deploy** and wait for the green **Ready**.
19. Copy the backend URL from the top of the page, e.g.
    `https://crm-backend.vercel.app`. Call this **[BACKEND URL]**.
20. Verify it works — open in a browser:
    ```
    https://crm-backend.vercel.app/health
    ```
    Expected: `{"status":"healthy"}`. Also open
    `https://crm-backend.vercel.app/docs` to see the API docs.

### PART 5 — Deploy the FRONTEND on Vercel (browser)

21. Open <https://vercel.com/new> again and import the **same** repo a second time.
22. **Project Name:** `crm-frontend`.
23. Click **Edit** next to **Root Directory** and select the **`frontend`** folder.
24. **Framework Preset:** leave **Vite** (auto-detected).
25. Expand **Environment Variables** and add:
    - `VITE_API_URL` → **[BACKEND URL]**  (e.g. `https://crm-backend.vercel.app`, **no trailing slash**)
26. Click **Deploy** and wait for **Ready**. Copy the frontend URL, e.g.
    `https://crm-frontend.vercel.app`. Call this **[FRONTEND URL]**.

### PART 6 — Connect the backend to the frontend (CORS)

27. Go to the **`crm-backend`** project → **Settings** → **Environment Variables**.
28. Edit `CORS_ORIGINS_RAW` so it includes the frontend URL:
    ```
    http://localhost:5173,https://crm-frontend.vercel.app
    ```
    (Use your real **[FRONTEND URL]**, no trailing slash, comma-separated.)
29. Go to **Deployments**, open the latest one, click **⋯ → Redeploy** so the
    backend picks up the new value.

### PART 7 — Verify end to end

30. Open **[FRONTEND URL]** in a browser. You should get the login page.
31. Open the browser **DevTools → Network** tab, try to log in, and confirm the
    request goes to `https://crm-backend.vercel.app/auth/login` and returns 200.
32. If you get a CORS error → recheck step 28 (exact origin, no trailing slash) and
    redeploy. If you get 404 → confirm the URL in `VITE_API_URL` (step 25).

### Reference: the values you should have written down

| Name | Where it comes from |
|------|---------------------|
| **[POOLED URL]** | Neon, Connection pooling **ON** |
| **[DIRECT URL]** | Neon, Connection pooling **OFF** (migrations only) |
| **[BACKEND URL]** | `https://crm-backend.vercel.app` (Vercel backend project) |
| **[FRONTEND URL]** | `https://crm-frontend.vercel.app` (Vercel frontend project) |
| **SECRET_KEY** | `python -c "import secrets;print(secrets.token_hex(32))"` |

## 1. Create the Neon database

1. Go to <https://console.neon.tech> and create a project (e.g. `crm`).
2. On the **Connect to your branch** dialog (the screen in your screenshot):
   - Keep **Branch**: `production` / `Default`
   - Keep **Database**: `neondb`
   - Keep **Role**: `neondb_owner`
   - Turn **Connection pooling ON** ← important for Vercel serverless
   - Copy the **Connection string** shown, e.g.:

     ```
     postgresql://neondb_owner:********@ep-nameless-bird-aoxabp16-pooler.c-4.us-east-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require
     ```

   This is the **pooled** URL — use it for the running application.

3. Also copy the **direct / non-pooled** URL (turn *Connection pooling OFF*).
   It has no `-pooler` in the host. You use this one **only to run
   migrations** (Alembic). Pooled (pgBouncer) connections can break DDL.

> 💡 Neon requires SSL. The app automatically appends `sslmode=require` if it
> is missing, but keeping it in the URL is best.
>
> If you ever see `invalid connection option "channel_binding"`, just remove
> `&channel_binding=require` from the URL — `sslmode=require` is enough.

## 2. Apply database migrations to Neon

The schema is managed by Alembic (`backend/alembic`). From your machine:

```bash
cd backend

# Windows (cmd)
set DATABASE_URL=postgresql://neondb_owner:********@ep-xxxx.c-4.us-east-1.aws.neon.tech/neondb?sslmode=require

# macOS / Linux
export DATABASE_URL="postgresql://neondb_owner:********@ep-xxxx.c-4.us-east-1.aws.neon.tech/neondb?sslmode=require"

alembic upgrade head
```

Use the **direct** (non-pooled) URL here. This creates all tables via the
initial migration `7cdabde502d3_initial_migration.py`.

> Every time you add a new migration file, run `alembic upgrade head` again
> against Neon (this is not run automatically by Vercel).
>
> To create a new migration after changing a model:
> ```
> alembic revision --autogenerate -m "describe your change"
> alembic upgrade head
> ```

## 3. Environment variables

These must be set in the Vercel project (and locally in `backend/.env` /
`frontend/.env`). Templates are provided: `backend/.env.example`,
`frontend/.env.example`.

### Backend

| Key | Value |
|-----|-------|
| `DATABASE_URL` | the **pooled** Neon URL (`...-pooler...?sslmode=require`) |

| Key | Value |
|-----|-------|
| `VITE_API_URL` | *(only for Option B)* the backend URL, e.g. `https://crm-backend.vercel.app` — no trailing slash |

## Option A — Single Vercel project with Services

This is the flow in your screenshot. Vercel detected two services and asked
for a `vercel.json`. One has already been added to the repo root:

**`vercel.json`** (repo root)

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "services": {
    "frontend": {
      "root": "frontend",
      "framework": "vite"
    },
    "backend": {
      "root": "backend",
      "framework": "fastapi"
    }
  }
}
```

### Steps

1. On the **New Project** screen, click **Refresh** next to *"vercel.json
   required to deploy projects with multiple services"*. Vercel should read the
   committed file above and show `frontend` (Web Service / Vite) and `backend`
   (Web Service / FastAPI).
2. Set **Root Directory** to `./` (the repository root).
3. Click **Deploy**.
4. After the first deploy, open **Settings → Environment Variables** and add
   the backend variables from the table above (`DATABASE_URL`, `SECRET_KEY`,
   `CORS_ORIGINS_RAW`, …). Scope them to the **backend** service / Production.
5. **Redeploy** so the backend picks up the variables.
6. Copy the deployment URL (e.g. `https://crm.vercel.app`). Add it to
   `CORS_ORIGINS_RAW` on the backend and redeploy if needed.

### How the frontend reaches the backend (Option A)

Two supported paths:

- **Same origin (default):** leave `VITE_API_URL` **unset**. The frontend calls
  `/api/...`, and Vercel routes `/api/*` to the `backend` service (this is the
  `/api` prefix shown next to the backend service in the Vercel UI).
- **Direct service URL:** set `VITE_API_URL` to the backend service URL Vercel
  shows under the `backend` service, and rebuild the frontend.

> ⚠️ The Services feature is relatively new. After the first deploy, open the
> frontend in a browser and check the Network tab:
> - If requests to `/api/...` return **404**, the backend is not receiving the
>   `/api` prefix without stripping. Set `VITE_API_URL` to the backend service
>   URL (Option A "Direct service URL") — this bypasses the routing ambiguity.
> - If requests fail with a **CORS** error, add the frontend origin to
>   `CORS_ORIGINS_RAW` on the backend.

## Option B — Two separate Vercel projects

Most predictable and the recommended fallback if Option A gives trouble. You
create **two** Vercel projects from the same GitHub repo, differing only in
**Root Directory**.

### B1. Backend project

1. **Add New → Project → Import** `eliteinovapythonbackend21-cyber/Crm`.
2. **Project Name**: `crm-backend`
3. **Root Directory**: `backend`  ← *Edit* and select the `backend` folder.
4. Framework Preset: Vercel auto-detects **FastAPI** (it sees `main.py` +
   `requirements.txt`).
5. **Environment Variables**: add the backend table above
   (`DATABASE_URL` = pooled Neon URL, `SECRET_KEY`, `CORS_ORIGINS_RAW`, …).
6. **Deploy**. Copy the resulting URL, e.g. `https://crm-backend.vercel.app`.

Optional — sanity check:

```bash
curl https://crm-backend.vercel.app/health
# {"status":"healthy"}
```

> If the backend build fails to find the app, add a `backend/vercel.json`:
> ```json
> { "framework": "fastapi" }
> ```
> and make sure `backend/main.py` exports `app` (it does).

### B2. Frontend project

1. **Add New → Project → Import** the same repo again.
2. **Project Name**: `crm-frontend`
3. **Root Directory**: `frontend`
4. Framework Preset: **Vite** (auto-detected).
5. **Environment Variables**:
   - `VITE_API_URL` = `https://crm-backend.vercel.app` (the URL from B1, no
     trailing slash)
6. **Deploy**. Copy the URL, e.g. `https://crm-frontend.vercel.app`.

### B3. Wire CORS

Go back to the **backend** project → Settings → Environment Variables and set:

```
CORS_ORIGINS_RAW=http://localhost:5173,https://crm-frontend.vercel.app
```

Redeploy the backend. Done.

The frontend already has a SPA rewrite (`frontend/vercel.json`) so deep links
like `/admin/dashboard` resolve to React Router instead of 404.

## Troubleshooting

| Symptom | Cause / Fix |
|---------|-------------|
| `KeyError: 'DATABASE_URL'` at boot | Env var not set on Vercel → add it and redeploy. |
| `invalid connection option "channel_binding"` | Remove `&channel_binding=require` from the Neon URL. |
| Only `alembic_version` exists, no other tables | The old baseline migration was empty. It is fixed now — run `DROP TABLE IF EXISTS alembic_version;` in Neon, then `alembic upgrade head` again, **or** just run `backend/seed_live.sql` (see PART 2b). |
| `relation "users" does not exist` | Migrations were not applied → run `alembic upgrade head` with the direct Neon URL, or run `backend/seed_live.sql`. |
| Can't log in (`Invalid username or password`) | The seed users were not inserted → run `backend/seed_live.sql` (it inserts `admin`/`Admin@123` and `employee1`/`Employee@123`). |
| CORS error in browser console | Frontend origin missing from `CORS_ORIGINS_RAW` (no trailing slash), then redeploy backend. |
| `/api/...` returns 404 (Option A) | Set `VITE_API_URL` to the backend service URL and rebuild. |
| Frontend 404 on refresh of `/admin/...` | SPA rewrite missing → `frontend/vercel.json` handles it when Root Directory is `frontend`. |
| `SSL connection is required` | Ensure `?sslmode=require` is in `DATABASE_URL`. |
| Serverless connection errors / timeouts | Use the **pooled** (`-pooler`) Neon URL for the app; connections are pre-pinged and recycled automatically. |
| `alembic` output says `Context impl SQLiteImpl` (not `PostgresqlImpl`) | A `DATABASE_URL` OS environment variable is set in your shell and overrides `backend/.env` (because `load_dotenv()` does not overwrite existing variables). Close the terminal / run `Remove-Item Env:DATABASE_URL`, then run `alembic upgrade head` again so the `.env` URL is used. |
| `alembic` says `Can't locate revision identified by '74f998e16407'` | Your DB still has the old stamp. In the Neon SQL Editor run `DROP TABLE IF EXISTS alembic_version;`, then `alembic upgrade head`. |
| PowerShell error `Unexpected token` / `filename ... syntax is incorrect` when running the command | The `$env:...` line and the `alembic` line were pasted onto one line. Put them on **separate lines**, or join with `;`. |
